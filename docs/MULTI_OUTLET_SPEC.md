# Alnadl Hospitality OS — Multi-Outlet Specification (§6, §8, §13, §26.1)

## تعريف Outlet
كيان تشغيلي ومالي مستقل ضمن منشأة واحدة — **وليس تصنيفًا داخل قائمة واحدة**. كل منفذ يحمل: نوعه (قهوة/مطعم/مخبز/خدمة/آخر)، الجهة المشغّلة (النادل/الشريك/طرف ثالث)، ساعات عمله، محطة تجهيزه (`station_id`)، نمط التسليم، أهداف SLA، ونموذج إيراده الخاص.

### الترحيل من Merchants (Phase 3)
كل منفذ يحمل `legacy_merchant_id` إن نشأ من ترحيل تلقائي — **جدول `merchants` القديم لم يُحذف ولم يُعدَّل**، يبقى يعمل بمعزل تام. راجع `migratePhase4Outlets()` في `db.js`.

## Service Hub — منطق الظهور
```
عدد المنافذ الفعّالة والمتاحة الآن (بعد فلترة الوقت/المكان) عند هذه النقطة:
  ≤ 1  →  تخطٍ كامل، لا شاشة إضافية (hub:false)
  > 1  →  عرض بطاقات الاختيار (hub:true) — فقط إن كانت الباقة تشمل multiOutlet
         وإلا: تدهور آمن لأول منفذ متاح (hub:false أيضًا، بلا خطأ)
```

## السلة الموحّدة (Unified Cart)
العميل يستطيع إضافة أصناف من أكثر من منفذ لنفس السلة (زر "منافذ أخرى" في القائمة). عند إتمام الطلب:
```
POST /api/orders
  → كل سطر يُحسم outlet_id تلقائيًا من product.outlet_id (لا يحتاج العميل تحديده)
  → إن كانت الأصناف من منفذ واحد: طلب عادي (orders فقط، بلا child_orders) — 100% كما قبل Phase 4
  → إن امتدت لأكثر من منفذ وكانت الباقة تشمل unifiedCart:
       تُنشأ صفوف child_orders (واحد لكل منفذ)، وتُربط order_items بالطلب الفرعي الصحيح
```

## آلة الحالة على مستوى الطلب الفرعي
نفس `lib/statemachine.js` تمامًا — لا منطق مختلف. الفرق الوحيد: نقطة نهاية منفصلة (`POST /api/child-orders/:id/transition`) بدل تعديل نقطة `POST /api/orders/:id/transition` القائمة (حفاظًا على صفر تأثير على الطلبات أحادية المنفذ).

## اشتقاق حالة الطلب الأصل (Parent)
```js
// من server.js — deriveParentStatus()
إن كان كل الأبناء "Delivered"        → Parent = "Delivered"
إن كان كل الأبناء "Cancelled"        → Parent = "Cancelled"
غير ذلك: Parent = أقل حالة تقدّمًا بين الأبناء النشطين (غير الملغاة)
```
**لا يُكتب `orders.status` مباشرة أبدًا عند وجود أبناء** — يُعاد حسابه فقط.

## توجيه KDS (Multi-Outlet Routing)
```
GET /api/ops/queue?stationId=xxx
  → طلبات أحادية المنفذ: تُعرض كما هي دائمًا
  → طلبات متعددة المنافذ: كل child_order يظهر كتذكرة مستقلة، بعلامة اسم منفذه،
    قابلة للفلترة حسب station_id
```

## سياسة التسليم — Grouped مقابل Separate (منجزة، Q01)
عند اكتمال أجزاء طلب من منافذ مختلفة، `properties.delivery_grouping` يحدد السلوك: `grouped` (الافتراضي، يطابق حرفيًا السلوك القديم قبل هذه الميزة) ينتظر Runner اكتمال كل الأبناء ليسلّمهم دفعة واحدة؛ `separate` يُسلِّم كل Child Order فور جهوزيته بمعزل عن البقية. مُختبَر آليًا (23 اختبارًا في `tests/api-phase4.js`) وبصريًا. راجع `docs/API_DOCUMENTATION.md` §21 لتفاصيل الـAPI (`PATCH /api/admin/properties/:id`).

## القيود المعروفة
- لا فواتير منفصلة لكل منفذ عند الدفع — دفعة واحدة موحّدة للعميل دائمًا (يطابق §8 "Checkout واحد")؛ التوزيع المالي يحدث داخليًا بعد النجاح فقط
- لا إلغاء/استرجاع جزئي على مستوى صنف مفرد بعد — الإلغاء متاح على مستوى الطلب الفرعي (Child) بالكامل فقط
