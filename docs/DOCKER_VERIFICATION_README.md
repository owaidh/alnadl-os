# R4-B — Real Docker Verification

سكربت تحقق يُنفّذ البنود التسعة على **Docker حقيقي فقط**. لا محاكاة لحاوية ولا لـVolume: ما يُراد إثباته هنا — البقاء عبر `restart`/`recreate`، والوكيل العكسي الحقيقي، والنسخ إلى وحدة منفصلة — **لا تستطيع أي محاكاة إثباته**، ومحاولة ذلك تُنتج «دليلًا» لا يُثبت ما يدّعيه.

**لا يُعدّل أي كود منتج.** يقرأ `Dockerfile` كما هو ويبني منه.

---

## المتطلبات المسبقة

| المتطلب | ملاحظة |
|---|---|
| **Docker** مثبَّت والـdaemon يعمل | `docker info` يجب أن ينجح |
| صلاحية الوصول للـsocket | أو تشغيل بـ`sudo` |
| **اتصال بالإنترنت** | يسحب `nginx:alpine` و`curlimages/curl` و`node:22-slim` |
| المنفذان `18787` و`18080` متاحان | يُستخدمان على المضيف |
| `curl` على المضيف | لفحوص `/ready` و`/health` |

يُشغَّل **من جذر المستودع** بعد استخراج الحزمة.

---

## متغيرات البيئة

كلها **اختيارية** — للسكربت قيم افتراضية صالحة للاختبار:

| المتغير | الافتراضي |
|---|---|
| `SESSION_SECRET` | `docker-verify-secret-of-sufficient-length-32plus` |
| `ADMIN_BOOTSTRAP_USERNAME` | `verifyops` |
| `ADMIN_BOOTSTRAP_PASSWORD` | `verify-strong-pass-1` |

> هذه اعتمادات **اختبار** لبيئة معزولة تُحذف بعد التشغيل. **لا تُستخدم في إنتاج حقيقي.**

## أمر التشغيل الواحد

```bash
bash scripts/docker-verify.sh
```

المخرَج: سطر `[PASS]` أو `[FAIL]` **مع دليله** لكل فحص، ثم ملخّص وسطر أخير:

```
REAL_DOCKER_VERIFICATION: PASS
```
أو `FAIL`. ورمز الخروج `0` عند النجاح و`1` عند الفشل، فيصلح لخط نشر آلي.

**المدة المتوقعة**: 3–5 دقائق (منها ~30 ثانية فترة سماح مقصودة، وسحب الصور أول مرة).

## التنظيف

**يُنظّف نفسه تلقائيًا** في نهاية كل تشغيل — نجح أم فشل.

وإن انقطع التشغيل في المنتصف:

```bash
bash scripts/docker-verify.sh --clean
```

يزيل الحاويات والشبكة والـVolumes والصورة والملفات المؤقتة.

## البنود التسعة وكيف تُثبَت

| # | البند | طريقة الإثبات |
|---|---|---|
| 1 | `docker build` ينجح | بناء فعلي + معرّف الصورة وحجمها + **عدّ ملفات المهاجرات داخل الصورة** |
| 2 | المهاجرات حتى 017 | `docker exec` يقرأ `schema_migrations` من قاعدة الـVolume |
| 3 | `/ready` يصل Ready | استدعاء HTTP حقيقي عبر المنفذ المنشور |
| 4 | حيّ بعد فترة سماح | انتظار **30 ثانية** ثم `docker inspect` (الحالة و`RestartCount`) + `/health` |
| 5 | البقاء بعد `restart` | بيانات تُنشأ عبر الواجهة الإدارية ← `docker restart` ← مقارنة العدّادات |
| 8 | البقاء بعد `recreate` | **حذف الحاوية كليًا** وإنشاء أخرى على نفس الـVolume ← الخطة ما زالت مرئية عبر الـAPI |
| 6 | الوكيل الموثوق | **nginx حقيقي** أمام التطبيق: مُزوَّر من اتصال مباشر ⇒ محجوب · وعبر وكيل موثوق ⇒ كل عميل بحزمته · وعميل واحد ⇒ ما زال محدودًا |
| 7 | النسخ إلى Volume منفصل | تنفيذ النسخ ← عدّ الملفات على **الـVolume الآخر** ← **والتحقق من صلاحيتها** لا مجرد وجودها |
| 9 | `APP_INSTANCES` | تشغيل بـ`4` ⇒ يجب أن يُرفض · والحاوية العاملة مؤكَّدة `=1` |

### ملاحظة على البند 7

`Dockerfile` **لا ينسخ `scripts/`** — الصورة تحمل ما يلزم التشغيل فقط، وهو قرار سليم يُبقي سطح الإنتاج ضيقًا. لذا يُركّب السكربت `scripts/` و`lib/` و`db.js` **للقراءة فقط** عند تنفيذ النسخ.

هذا يعكس التشغيل الواقعي: **النسخ الاحتياطي مهمة صيانة** تُنفَّذ من المضيف أو من حاوية أدوات ضد نفس الـVolume، لا من صورة التطبيق نفسها. وإن فضّلت تنفيذه بـ`docker exec` داخل حاوية التطبيق، فذلك يتطلب إضافة `COPY scripts ./scripts` — **وهو تغيير في المنتج لم أُجرِه**، وأتركه قرارًا لك.

---

## ماذا أرسل لي

**المخرَج كاملًا** من أول سطر حتى `REAL_DOCKER_VERIFICATION:`. أحتاج الأدلة لا الحكم وحده — فسطر `PASS` بلا دليله لا يُراجَع.

إن فشل أي بند، السكربت يطبع **سجل الحاوية** مع الفشل، وهو عادةً كافٍ للتشخيص.
