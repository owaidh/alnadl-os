# R4-B — Real Docker Verification

سكربت تحقق يُنفّذ البنود التسعة على **Docker حقيقي فقط**. لا محاكاة لحاوية ولا لـVolume: ما يُراد إثباته هنا — البقاء عبر `restart`/`recreate`، والوكيل العكسي الحقيقي، والنسخ إلى وحدة منفصلة — **لا تستطيع أي محاكاة إثباته**، ومحاولة ذلك تُنتج «دليلًا» لا يُثبت ما يدّعيه.

**لا يُعدّل أي كود منتج.** يقرأ `Dockerfile` كما هو ويبني منه.

## المتطلبات المسبقة

| المتطلب | ملاحظة |
|---|---|
| **Docker** مثبَّت والـdaemon يعمل | `docker info` يجب أن ينجح |
| صلاحية الوصول للـsocket | أو تشغيل بـ`sudo` |
| **اتصال بالإنترنت** | يسحب `nginx:1.27-alpine` و`curlimages/curl:8.6.0` و`node:22-slim` |
| المنفذ `18787` متاح | يُستخدم على المضيف |
| الشبكة الفرعية `172.28.77.0/24` غير مستخدمة | عناوين ثابتة للعملاء |
| `curl` على المضيف | لفحوص `/ready` و`/health` |

يُشغَّل **من جذر المستودع** بعد استخراج الحزمة.

## أمر التشغيل الواحد

```bash
bash scripts/docker-verify.sh
```

المخرَج: سطر `[PASS]` أو `[FAIL]` **مع دليله** لكل فحص، ثم ملخّص وسطر أخير:

```
REAL_DOCKER_VERIFICATION: PASS
```
أو `FAIL`. ورمز الخروج `0` عند النجاح و`1` عند الفشل، فيصلح لخط نشر آلي.

**المدة المتوقعة**: 3–5 دقائق (منها ~30 ثانية فترة سماح مقصودة، وسحب الصور أول مرة).

## التنظيف

**يُنظّف نفسه تلقائيًا** عبر `trap cleanup EXIT INT TERM` — فيسري على **النجاح والفشل والمقاطعة بـCtrl-C** معًا.

وإن انقطع التشغيل في المنتصف:

```bash
bash scripts/docker-verify.sh --clean
```

يزيل الحاويات والشبكة والـVolumes والصورة والملفات المؤقتة.

## البنود التسعة وكيف تُثبَت

| # | البند | طريقة الإثبات |
|---|---|---|
| 1 | `docker build` ينجح | بناء فعلي بـ`--pull` + معرّف الصورة وحجمها + **عدّ ملفات المهاجرات داخل الصورة** |
| 2 | المهاجرات حتى 017 | `docker exec` يقرأ `schema_migrations` من قاعدة الـVolume |
| 3 | `/ready` يصل Ready | استدعاء HTTP حقيقي عبر المنفذ المنشور |
| 4 | حيّ بعد فترة سماح | انتظار **30 ثانية** ثم `docker inspect` (الحالة و`RestartCount`) + `/health` |
| 5 | البقاء بعد `restart` | **طلب حقيقي** — انظر أدناه |
| 8 | البقاء بعد `recreate` | **نفس الطلب** بعد حذف الحاوية كليًا |
| 6 | الوكيل الموثوق | **nginx حقيقي + عميلان ثابتان** — انظر أدناه |
| 7 | النسخ إلى Volume منفصل | تنفيذ النسخ ← عدّ الملفات على **الـVolume الآخر** ← **والتحقق من صلاحيتها** لا مجرد وجودها |
| 9 | `APP_INSTANCES` | تشغيل بـ`4` ⇒ يجب أن يُرفض · والحاوية العاملة مؤكَّدة `=1` |

### البقاء (5 و8) — طلب حقيقي لا عدّ جداول

يُبنى مستأجر كامل عبر الواجهة الإدارية (باقة ← شريك ← تفعيل ← منطقة ← نقطة ← فئة ← منتج)، ثم **طلب حقيقي عبر الرحلة**: إنشاء ← دفع ← `Accepted` ← `Preparing` ← `Ready` ← `Out for Delivery` ← `Delivered`.

**اللقطة المرجعية تُسجّل**:

| الحقل | لماذا |
|---|---|
| `order_id` و`status` | الادعاء نفسه: «لا تُفقد الطلبات» |
| `partner_id` · `property_id` · `zone_id` · `point_id` | الروابط الأساسية — طلب بلا روابطه بيانات ميتة |
| عدد `order_items` و`total` | محتوى الطلب لا وجوده فقط |
| `payments` المُحصَّلة ومجموعها | الربط المالي |
| صفوف `revenue_ledger` | أثر الإيراد |
| الباقة `DOCKERVERIFY` وحالة الشريك | الإعدادات |

تُقارَن اللقطة **حرفيًا** قبل وبعد `restart`، ثم بعد **حذف الحاوية وإنشاء أخرى** على نفس الـVolume — **مع قراءة الطلب مرة أخرى عبر الـAPI** لا من القاعدة وحدها. ويُتحقَّق أن المهاجرات **لم تُعَد** على قاعدة قائمة.

> `restart` يُبقي نفس الحاوية؛ **`recreate` وحده يُثبت** أن البيانات على الـVolume لا داخل الطبقة القابلة للكتابة.

### الوكيل الموثوق (6) — عميلان ثابتان بعنوانين مثبتين

شبكة بشبكة فرعية معرَّفة (`172.28.77.0/24`) وعناوين ثابتة: التطبيق `.10` · nginx `.20` · **العميل A `.31`** · **العميل B `.32`**.

**لماذا حاويتان دائمتان**: إنشاء حاوية curl جديدة لكل «عميل» **لا يُثبت الفصل** — الحاويات المتعاقبة قد تُعيد استخدام نفس العنوان فيبقى المجموع تحت الحد بلا أن يكون هناك فصل أصلًا.

**التسلسل**:
1. **العميل A** يستنفد حزمته حتى `429`
2. **العميل B** عبر **نفس** nginx الموثوق ⇒ طلبه يمرّ — حزمة مستقلة
3. **العميل A** يُعاد فحصه ⇒ **ما زال `429`** — فنجاح B لم يُصفّر حزمة A ولم يتشاركا واحدة
4. **العميل A يحشو XFF مزيفًا** عبر الوكيل ⇒ ما زال محجوبًا (يُقرأ آخر عنصر لا أوله)

وقبل ذلك: **مُزوَّر من اتصال مباشر غير موثوق** ⇒ لا يُغيّر الهوية إطلاقًا.

### إعادة الإنتاج

الصور **مثبَّتة بإصداراتها**: `curlimages/curl:8.6.0` · `nginx:1.27-alpine`. لا `:latest` — وإلا تغيّرت نتيجة التحقق بلا تغيير في الشيفرة.

### ملاحظة على البند 7

`Dockerfile` **لا ينسخ `scripts/`** — الصورة تحمل ما يلزم التشغيل فقط، وهو قرار سليم يُبقي سطح الإنتاج ضيقًا. لذا يُركّب السكربت `scripts/` و`lib/` و`db.js` **للقراءة فقط** عند تنفيذ النسخ.

هذا يعكس التشغيل الواقعي: **النسخ الاحتياطي مهمة صيانة** تُنفَّذ من المضيف أو من حاوية أدوات ضد نفس الـVolume، لا من صورة التطبيق نفسها. وإن فضّلت تنفيذه بـ`docker exec` داخل حاوية التطبيق، فذلك يتطلب إضافة `COPY scripts ./scripts` — **وهو تغيير في المنتج لم أُجرِه**، وأتركه قرارًا لك.

## ماذا أرسل لي

**المخرَج كاملًا** من أول سطر حتى `REAL_DOCKER_VERIFICATION:`. أحتاج الأدلة لا الحكم وحده — فسطر `PASS` بلا دليله لا يُراجَع.

إن فشل أي بند، السكربت يطبع **سجل الحاوية** مع الفشل، وهو عادةً كافٍ للتشخيص.
