# PostgreSQL Production Migration — خطة التنفيذ ومتطلبات البيئة

> **حالة البند: Not Implemented.** النظام يعمل على SQLite. هذه الوثيقة **ليست ادعاءً بالإنجاز** — هي تدقيق حقيقي للشيفرة القائمة، ومواصفة البيئة اللازمة للتنفيذ.

---

## 1. لماذا لم يُنفَّذ — إثبات لا ادعاء

جُرِّبت **أربع طرق مستقلة** للحصول على PostgreSQL في بيئة التطوير الحالية:

| المحاولة | النتيجة الفعلية |
|---|---|
| البحث عن ثنائيات `postgres`/`pg_ctl`/`psql` في كل المسارات | **غير موجودة** |
| `apt-get install postgresql` (تنفيذ فعلي) | **`403 Forbidden`** من `archive.ubuntu.com` و`security.ubuntu.com` |
| `npm install pg` | **`403 Forbidden`** من `registry.npmjs.org` |
| البحث عن خادم مستمع أو متغيرات اتصال خارجية | **لا شيء** |

> ملاحظة مهمة: `apt-get install -s` (محاكاة) **تنجح** لأنها تقرأ بيانات الحزم من ذاكرة محلية — لكن التنزيل الفعلي محجوب. الاعتماد على المحاكاة وحدها كان سيُنتج ادعاءً خاطئًا.

**الخلاصة**: التحقق الحقيقي على PostgreSQL **مستحيل تقنيًا في هذه البيئة**. ولم تُحاكَ PostgreSQL ولم تُعدَّل أي اختبارات لتمريره.

## 2. المتطلب التقني المحدد — ما نحتاجه بالضبط

### الحد الأدنى للتشغيل

| المتطلب | التفصيل |
|---|---|
| **خادم PostgreSQL 15+** | نسخة محلية أو مُدارة (RDS / Cloud SQL / Supabase) قابلة للوصول من بيئة البناء |
| **بيانات الاتصال** | `DATABASE_URL=postgres://user:pass@host:5432/dbname` — ويُفضَّل قاعدتان: `alnadl_test` و`alnadl_staging` |
| **مكتبة `pg`** | إما شبكة مفتوحة لـ`registry.npmjs.org`، أو تزويدنا بحزمة `pg` مُثبَّتة مسبقًا في `node_modules` |
| **صلاحيات** | `CREATE TABLE` · `CREATE INDEX` · `ALTER TABLE` · وصلاحية إنشاء/إسقاط قاعدة اختبار |

### للتحقق الكامل من بنود §3.1 الستة

| البند المطلوب | يحتاج إضافةً |
|---|---|
| اختبار ترحيل بيانات موجودة | **نسخة بيانات Staging ممثلة للواقع** (أو إذن بتوليد مجموعة تمثيلية) |
| Backup → Restore | صلاحية `pg_dump` / `pg_restore` وقرص للنسخ |
| التزامن (Concurrency) | إمكانية فتح عدة اتصالات متزامنة (Connection Pool) |

## 3. تدقيق قابلية النقل — جرد حقيقي من الشيفرة

فُحصت الشيفرة فعليًا. النتائج أدناه **عدّ حقيقي بمواضع محددة**، لا تقدير.

### 3.1 العائق المعماري الأكبر — التزامن مقابل اللاتزامن

| القياس | القيمة |
|---|---|
| استدعاءات `db.prepare()` | **515** |
| الملفات المتأثرة | **35** |

`node:sqlite` يستخدم `DatabaseSync` — واجهة **متزامنة** (`.get()` / `.run()` / `.all()` تُرجع النتيجة مباشرة). واجهة `pg` **لا متزامنة** حصرًا.

**الأثر الحقيقي**: هذا ليس تبديل مُشغِّل (Driver Swap)، بل **تغيير معماري متتالٍ**: كل استدعاء يصبح `await`، فكل دالة تحتويه تصبح `async`، فكل مُستدعٍ لها يصبح `async` — وهكذا صعودًا عبر الشيفرة كاملة، بما فيها المهاجرات والعامل (Worker) والاختبارات.

**لماذا لم يُنفَّذ هذا التحويل "استباقيًا"**: تحويل 515 موضعًا عبر 35 ملفًا **دون قدرة على التحقق على PostgreSQL** يعني تغييرًا ضخمًا عالي المخاطر يهدد 700 اختبارًا ناجحًا مقابل فائدة **غير مُثبَتة**. القرار الهندسي الصحيح هو التنفيذ **مع** التحقق، لا قبله.

### 3.2 تراكيب SQL خاصة بـSQLite — الجرد الكامل

| التركيب | العدد | المواضع | البديل في PostgreSQL |
|---|---|---|---|
| `INSERT OR REPLACE` | 2 | `tests/partner-dashboard.js:63` · `lib/verification.js:61` | `INSERT ... ON CONFLICT (...) DO UPDATE` |
| `json_extract(x, '$.k')` | 5 (شيفرة) + 6 (اختبارات) | `lib/engage-ledger.js:50,94` · `lib/engage-mechanic-lab.js:263,269` | `x::jsonb ->> 'k'` |
| `PRAGMA table_info` | 1 | `migrations/015` | `information_schema.columns` |
| `PRAGMA journal_mode/foreign_keys/busy_timeout` | 3 | `db.js` | لا مقابل — PostgreSQL يديرها داخليًا (تُحذف) |
| `rowid` | 2 | `server.js:1469-1470` | عمود صريح أو `created_at` |
| `LIMIT ?` (معلمة مربوطة) | 4 | `engage-ledger.js:54` · `loyalty.js:150` · `server.js:1755,1782` | مدعوم في `pg` — يحتاج تحقق فقط |
| الطوابع الزمنية `INTEGER` | 33 تعريفًا | `db.js` | `BIGINT` يعمل مباشرة · الترقية لـ`timestamptz` قرار منفصل |

> **ملاحظة مطمئنة**: لا يوجد أي استخدام لـ`datetime('now')` أو `strftime` — الأوقات كلها تُولَّد في JavaScript وتُخزَّن كأعداد صحيحة، وهذا **يُبسِّط النقل كثيرًا**.

### 3.3 المهاجرات

المهاجرة **001** و**015** تستخدمان نمط **إعادة بناء الجدول** (إنشاء جدول جديد ← نسخ ← إسقاط ← إعادة تسمية) — وهو حلّ التفافي لقيد SQLite في إسقاط قيود الأعمدة.

**في PostgreSQL هذا غير ضروري**: `ALTER TABLE ... DROP CONSTRAINT` و`ADD CONSTRAINT` مدعومان مباشرة — أي أن المهاجرات ستُصبح **أبسط**، لا أعقد.

كذلك الفهرس الجزئي في المهاجرة 015 (`CREATE UNIQUE INDEX ... WHERE partner_id IS NOT NULL`) **مدعوم بصيغته نفسها** في PostgreSQL.

## 4. خطة التنفيذ المقترحة — بمراحل تحقق متدرجة

| المرحلة | المخرج | معيار القبول |
|---|---|---|
| **1. طبقة الوصول** | واجهة مُشغِّل موحّدة (`query`/`transaction`) مع مُشغِّلَي SQLite وPostgreSQL | كل الاختبارات تعمل عبر الطبقة على SQLite |
| **2. تطبيع SQL** | معالجة البنود السبعة في §3.2 | لا تراجع على SQLite |
| **3. التحويل اللاتزامني** | 515 موضعًا → `async/await`، ملفًا ملفًا | **700/700 على SQLite بعد كل ملف** |
| **4. مخطط PostgreSQL** | المهاجرات تعمل فعليًا على PG 15+ | إنشاء ناجح + فهارس + قيود |
| **5. التحقق الوظيفي** | تشغيل الاختبارات كاملة على PG | **700/700 على PostgreSQL** |
| **6. ترحيل البيانات** | سكربت SQLite → PG قابل للتكرار | تطابق العدّ والمجاميع المالية |
| **7. التزامن والمعاملات** | اختبارات تزامن على المسارات المالية | لا ازدواج دفع أو طلب |
| **8. النسخ والاستعادة** | `pg_dump` → `pg_restore` → تحقق | سلامة البيانات بعد الاستعادة |

**SQLite تبقى للتطوير والاختبار** كما طلبتم — الطبقة في المرحلة 1 تجعل الاثنين يتعايشان، و**الإنتاج يُصبح PostgreSQL صراحةً** عبر `DATABASE_URL`.
